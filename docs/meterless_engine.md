# Meterless World Model engine - what we followed and what we built

## Source

- Engines page: https://meterless.ai/engines.html - the World Model card's official prompt reads:
  *"Implement the Meterless World Model in this codebase: read `engines/world-model/AGENTS.md` at
  https://github.com/Meterless/Meterless and follow it to add an event-sourced shared state that every agent reads and writes."*
- Spec we followed: https://github.com/Meterless/Meterless/blob/main/engines/world-model/AGENTS.md
  (plus `docs/stable-ids.md`, `docs/ingest-pipeline.md`, `docs/read-surface.md`, `docs/concurrency-and-queues.md`).
- Reference implementation used as the guide (the spec says to diff against it): `engines/world-model/reference/` (TypeScript).
- Definition of done in the spec: *"run the conformance suite against your build ... a green scorecard is the definition of done"*
  (`conformance/runner.ts`, 8 checks).

## What the spec requires (and where it is in our code)

| Spec requirement | Our implementation |
|---|---|
| One canonical store, derived views; append-only event log, state is a fold over it | `engines/world_model/store.py` (`EventStore`) |
| Stable, content-derived IDs: `type:system:externalId` and `ent_` + sha256(`type:normalizedName`)[:16]; NFKD normalisation | `engines/world_model/stable_ids.py` |
| Banded merge resolution: >= 0.85 auto-merge, [0.82, 0.85) review queue, < 0.82 new | `engines/world_model/resolve.py`, `world.py` |
| Five write primitives (entity, context, relationship, fact, ingest), every write carries provenance ("no provenance, no write") | `engines/world_model/world.py` |
| Bitemporal edges: a superseding edge closes the old one, point-in-time queries | `store.py` fold, `GraphView.neighbors_of(at=...)` |
| Idempotent 10-step ingest cycle, Jaccard >= 0.5 story clustering, bucketed velocity | `engines/world_model/ingest.py` |
| Audit entry for every mutation, strictly ordered | `WorldModel.audit()` |
| Single-writer discipline (concurrent writers serialize) | one re-entrant lock per `WorldModel` |
| Read surface: graph / facts / snapshot (time travel) / timeline views | `world.py` views |
| Persistence with replay on load | JSON event log, `logs/world_state_<run_id>.json` |

## Verification (all green)

1. **Official suite on the official reference** - we installed the TypeScript reference and ran the Meterless
   `conformance/runner.ts` against it: **8/8 checks pass** (this proves we ran the suite correctly).
2. **The same 8 checks, ported 1:1 to Python** against our engine (`tests/test_world_model_engine.py`,
   ids `sid-001 sid-002 band-001 prov-001 idem-001 idem-002 bitemp-001 audit-001`): **8/8 pass**.
   The official runner is TypeScript-only and imports a TS module, so it cannot load a Python engine directly.
3. **Cross-validation against the reference ("golden" data).** `tests/data/world_model_golden.json` was generated by running
   the TS reference. Our Python engine reproduces it exactly: normalised names, entity ids, sha-256, canonical JSON, relationship /
   fact / context ids, similarity and merge bands, and **the full canonical world state after an ingest, byte for byte**.
4. Vidhur-level tests (`tests/test_world_model.py`): writes by one agent are visible to another, the Evaluator reads the claim from
   the world state and writes its verdict back, a run's final state holds plan + claims + verdicts + impacts, concurrent writers
   serialize into one ordered log, and the persisted file replays to the same state.

## Two places where we deliberately differ from the reference (both documented, both tested)

1. **Fact landing is inside the fold.** In the reference, `assertFact` writes the winning value onto the entity *outside* the event
   log, so replaying the log does not reproduce it - which contradicts the spec's own rule that state is a fold over the log.
   We apply the conflict policy inside the store's fold; the canonical state is unchanged (the golden test proves it) and a persisted
   run now replays to the identical state.
2. **`None` means "undefined"** in canonical JSON (the TS `undefined` is dropped; JS `null` has no Python distinction). Only affects
   explicit nulls, which Vidhur never writes.

Not ported: the browser control plane (UI), the merge-review UI, the H-MEM sync, and the embedding-similarity merge path (name
similarity only, as in the reference).

## How Vidhur uses it (`core/shared_state.py`)

One `WorldModel` per run, persisted to `logs/world_state_<run_id>.json`. All agents write and read through `RunWorld`:

| Who | Writes | Reads |
|---|---|---|
| Planner | `plan`, one `delegation` entity per decision (run or skip, with reason), its review decision | outcomes of every delegation (for the review) |
| Analysts | `claim` entities (one per attempt, linked `revised-into`), fetched `article` observations (ingest) | the Evaluator's feedback on their previous claim (to revise) |
| Evaluator | `verdict` entities linked to the claim (`audited-by`) | **the claim** it is judging (it receives only the claim's key) |
| Impact | `impact` entities linked to the claim (`has-impact`) | the final claim |
| Brief | nothing | **everything** (`RunWorld.report()`): the CFO brief is built from the world state only |

Entity ids follow the spec's grammar, e.g. `claim:vidhur:<run>-D1-a2`, `verdict:vidhur:<run>-D1-a2`.
